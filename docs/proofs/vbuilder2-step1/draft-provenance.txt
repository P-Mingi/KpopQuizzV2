RECEIPT 2 - THE WRITE PATH   (all three server rails already exist)
===========================================================================

1. AUTOSAVE WRITES DRAFT ONLY.  EXISTS today.
   POST /api/verse/presentation  (src/app/api/verse/presentation/route.ts)
   - Curator+ gate (canCurateSpace, else 403).
   - Runs the FULL validator server-side FIRST (SEO invariant: seoCritical blocks
     cannot be removed/hidden; WCAG-AA readability; sticker/tab caps; unknown block
     types) - rejects with 422 + human-readable errors before any write.
   - Upserts verse_spaces.presentation_draft ONLY (+ updated_at). It never touches
     `presentation` (live). This is exactly the background-save target for step 3.

2. PUBLISH = VALIDATE + PROMOTE + REVISION.  EXISTS today.
   POST /api/verse/presentation/publish  (.../presentation/publish/route.ts)
   - Curator+ gate.
   - Re-validates the draft at the gate (422 on failure).
   - Writes a verse_revisions row (entity_type='space_presentation',
     entity_id=<groupId>, section_key='presentation') as the append-only snapshot;
     on the FIRST publish it also snapshots the OUTGOING live look as a baseline so
     rollback can undo even the first publish (V-POLISH root-cause fix).
   - Then flips live: verse_spaces.presentation = validated draft.

3. ROLLBACK VIA THE EXISTING REVISION RAILS.  EXISTS today.
   POST /api/verse/presentation/rollback  (.../presentation/rollback/route.ts)
   - Curator+ gate.
   - Reads the space_presentation revisions (desc, limit 20). Target = a specific
     revision_id, or list[1] (list[0] is the current live snapshot, list[1] the
     previous look). Re-validates, sets BOTH live + draft to the restored content,
     and records the rollback as a new append-only revision.
   (History is surfaced by /api/verse/history; fold by /api/verse/presentation/fold.)

confirm dialog is client chrome around it.
