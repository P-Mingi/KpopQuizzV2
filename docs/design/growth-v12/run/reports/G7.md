### The card (prototype `#e-tot`, states `quiz-bonus`, `quiz-bonus-voted`)

Between the result actions and "Keep playing". On mount it asks `GET /api/duel/pairs?group=<the quiz's group>`
with the browser id (`lib/anon-id.ts`, header `x-duel-anon`). No pair = no card (nothing is reserved, nothing is
shown). With pairs: kicker, "Which one do you replay more?", the dots, two songs (title, group, year when the
catalogue has one, Deezer cover asked at 264px), "Skip". A tap sends the vote; the answer carries the real split
of that pair, the picked song gets the pink ring, the shares and the bars appear, the message says "You agree with
54% of ARMY", focus goes to "Next pair" ("Finish" on the last one). Up to 5 pairs. Skip ends the bonus: with at
least one vote the card thanks and says "2 of 5 pairs"; with none it leaves.

What is never invented:
- The split shows only when the pair has 5 votes or more, the fan's included. Under that: "Vote counted. This
  pair needs more votes before it shows a split." (no percent, no bar).
- The year is hidden when the catalogue has none for the song ("BTS" instead of "BTS · 2019").
- The fandom name comes from `groups.fandom_name` through `realFandomName` (placeholders like "fan" are not
  fandoms): without one the copy says "fans".
- "Your votes are in ARMY's top 10" and the "See what ARMY picked" link show only when the group has a ranking;
  otherwise "Your votes count toward ARMY's top 10" and no link.
- A refused or failed vote is said ("Your vote was not saved. Tap again.") and is not counted in "n of 5 pairs".

### Anti-abuse

In `castVote` (`lib/duel/service.ts`), in this order:

1. The pair token must be one this server signed and not expired (2 hours). A vote for a pair the server did not
   issue is refused (403) before any database call.
2. The token must have been issued to the same voter hash (403).
3. A signed-in editorial account never votes (403; `editorial_accounts`, when the table exists).
4. Burst limit: 30 votes a minute per voter hash, in memory (429). Pairs: 20 requests a minute.
5. In the database, atomically (`duel_cast_song_vote`): the question is an active song question, both songs
   belong to it, **one vote per pair per voter per UTC day** (primary key of `duel_vote_guard`, A-B and B-A are
   the same pair), 200 votes a day per voter at most.

Voter hash only: HMAC-SHA256 of `u:<user id>` (signed in) or `a:<browser id>`, 32 hex characters. No IP, no user
agent and no user id is stored or even read. The function is granted to `service_role` only, so a direct call
with the anon key is refused: the route is the only way in.

### The ranking

`lib/duel/bradley-terry.ts`: the MM iteration (Hunter 2004), deterministic (same votes in any order = same
ranking), equal strengths share a rank (1, 1, 3). One regulariser, part of the model and never shown: each song
also plays one virtual comparison against an average opponent and wins half of it, which keeps a never-beaten
song finite.

`lib/duel/fans-picked.ts`: weekly movement needs no history table. The ranking is computed twice from the same
vote log, with every counted vote and with the votes older than 7 days; movement = last week's rank minus today's
rank. A song that had no rank a week ago has no movement (null).

Thresholds, and why (constants at the top of `fans-picked.ts`):
- **A group is ranked from 100 counted votes** (`MIN_VOTES_FLOOR`), or `duel_questions.min_votes` when that is
  higher (500 on the three existing questions, which already have 1,160 to 2,262). A group has up to 16 songs,
  so 100 votes is about 12 comparisons per song; under that one fan (5 pairs per quiz result) can reorder the top
  alone. Under the threshold the API says `ranked: false` and gives no song.
- **A song is ranked from 5 comparisons** (`MIN_SONG_COMPARISONS`): one lucky vote would otherwise put it first.
- Editorial accounts' votes are excluded by their voter hash (when the table exists; today it does not).

The cron stores one row per song in `duel_song_rankings` and prunes `duel_vote_guard` rows older than 2 days (its
own tables only; `duel_votes` is only read, page by page because of the 1000-row cap).

Dry run against production (`?dry=1`, reads only, `run/reports/G7/cron-dry-run.txt`): aespa 2,262 votes, 12 of 12
songs ranked; BLACKPINK 1,282, 16 of 16; BTS 1,160, 16 of 16. The totals equal the table counts of section 1.
No vote was cast in the last 7 days (the old feature was closed on 2026-09-19), so the first movement is 0
everywhere, which is true.

## 3. The Fans picked API (for G8)

`GET /api/duel/fans-picked?group=<slug>` or, in a server component, `getFansPicked(slug)` from
`@/lib/duel/server` (never throws). Type `FansPickedResponse` in `lib/duel/types.ts`:

```ts
{
  group: { slug: string; name: string; fandom: string | null } | null,
  ranked: boolean,          // false = hide the section
  votes: number | null,     // counted votes on the group's songs
  minVotes: number,         // votes needed before the group is ranked
  hasMovement: boolean,     // the group already had a ranking 7 days ago
  updatedAt: string | null, // ISO time of the last nightly run
  songs: Array<{            // top 10, best first; [] unless ranked
    id: string; title: string; year: number | null; cover: string | null,
    rank: number,           // equal strengths share a rank
    votes: number,          // counted votes this song took part in
    movement: number | null,// places gained (+) or lost (-) in 7 days; null = no rank a week ago
    isNew: boolean,
  }>,
}
```

Section anchor to use on the hub: `id="fans-picked"` (the card links to `/<slug>-quiz#fans-picked`). "Vote" can
mount `<ThisOrThatBonus groupSlug groupName />`. Details: `run/requests/G7.md` R2.

`GET /api/duel/pairs?group=<slug>` (header `x-duel-anon`) answers `{ pairs: [{ token, a, b }], group, ranked }`;
`POST /api/duel/vote { token, winner: 'a' | 'b' }` answers `{ status: 'ok' | 'already_voted', split: { a, b,
total } | null }` or `{ error }` with 400, 403, 429 or 503.

## 10. Owner decisions (none blocks)

1. **Which groups get the card.** `v12-g7-song-questions.sql` opens it to 77 more groups with their 16 most
   played songs on Deezer. Without `v12-g7-this-or-that.sql` no group gets the card (no pair is issued while
   that file is not applied); with it and without `v12-g7-song-questions.sql`, only aespa, BLACKPINK and BTS
   have it (issue C2-004, corrected in fix loop 1). A shorter list of groups, or
   title tracks only once G2's title-track data is in, is a change of one `where` line.
2. **Thresholds.** A group is ranked from 100 votes (500 for the three old questions, already passed), a song
   from 5 comparisons, a split shows from 5 votes on the pair, 200 votes a day per voter.
3. **Signing key.** Derived from the service role key unless `DUEL_SIGNING_SECRET` is set (request R3).
4. **Years.** Most songs have no year in the catalogue (156 of 4,120); the card then shows the group name alone.
   34 of the 44 songs of the three live questions get one from the blindtest list.
5. **Old Elo columns.** New votes do not update `duel_ratings.elo / wins / losses` (the pre-V12 live Elo of
   `cast_duel_vote`, whose pages were removed in REFONTE P1). The Bradley-Terry table replaces them. The old
   75,191 votes all count in the new ranking, with their old ip-and-day voter hashes left as they are.
