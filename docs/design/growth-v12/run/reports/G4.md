How it works
- The host tab drives the game through `POST /api/live/rooms/<code>/host` with a host token (shown once, kept in
  the browser, only its sha256 in the database). A phone joins with a nickname, gets a player token the same way,
  and sends one answer per round to `/answer`. A phone never sends on the channel.
- Server time: the round starts at the database's `clock_timestamp()`, and the answer time is measured by the
  same clock inside the function that stores the answer. Late (after the round's seconds) and second answers are
  refused in that same statement. No browser clock and no API server clock decides a score.
- Scores are computed at the reveal by `lib/live/scoring.ts` and written in one transaction, once per round
  (`scored_round` guard). A phone learns whether it was right only at the reveal.
- Realtime: private channel `live:<room id>`. The pending SQL adds one SELECT policy on `realtime.messages` (anon
  and authenticated may receive broadcasts of an open room) and no INSERT policy, so a browser can neither
  broadcast nor track presence. The server broadcasts the public state with the service role over the Realtime
  HTTP endpoint after: round start, reveal, leaderboard, end, play again, a removal, the close. Nothing in a
  broadcast is secret (no answer before the reveal, no clip, no token).
- Joins and answers are NOT broadcast: the host screen polls its state once a second in the lobby and during a
  round. One broadcast costs one delivery per phone; broadcasting 50 answers to 50 phones every round would
  spend the message quota for nothing a phone shows. A game costs 3 broadcasts per round.
- Resilience: a phone reads the state route with its token on every (re)subscription, when the tab comes back,
  every 20 s as a safety net, and every 2.5 s while the channel is down. The token is the player, so a phone that
  drops keeps its score. A host reload reads the room back from the state route; if the timer ran out meanwhile
  it asks for the reveal at once.
- Moderation: the nickname goes through the site's list (`verse_banned_terms`, the table `lib/verse/moderation.ts`
  uses), with a stricter match than comments (inside a word, through spacing, punctuation and digits used as
  letters, for terms of 4 letters or more). The host removes a player from the "Players" sheet: the token is then
  refused (403).
- Limits: 50 players (decided under the room's row lock), 10 rooms per hashed address per 10 minutes, 6
  character codes unique among open rooms, rooms gone two hours after they open.
- Tracking: each phone records one run through `trackBtRun()` (`source = 'live'`, `playlist = 'live:<code>'`,
  `mode = 'classic'`): start when the first round reaches it, finish at the podium, or `completed = false` if it
  leaves. The host screen records nothing (it is not a player). Nothing is sent when `NEXT_PUBLIC_BT_TRACKING`
  is off.

## 5. The QR encoder

`lib/live/qr.ts`, no dependency. Proof beyond its own tests: `qr.test.ts` holds an independent reader (it finds
the function modules itself, removes the mask, undoes the interleaving, checks every block with Reed-Solomon
syndromes, parses the bytes) and reads back every version from 1 to 10 at the four levels and the eight masks;
the tables are checked against the standard (codeword totals, capacities, format and version bits, the textbook
Reed-Solomon block). And six codes were rendered and read by a reader I did not write, macOS Vision
(`VNDetectBarcodesRequest`): the join link at M and H (versions 3 and 4), a 100 character share link (v8, Q), 213
bytes (v10, M), a URL with an escaped accent (v3, L) and one letter (v1): 6 of 6 read back exactly.

## 11. Owner decisions and questions

1. **Realtime limits (needed before the load test and before promoting the mode).** In the Supabase dashboard,
   Realtime settings of the project: concurrent connections, messages per second, channel joins per second, and
   the plan's included messages per month. One room is up to 50 connections (51 if the host plays along) and
   about 150 deliveries per round (3 broadcasts x 50 phones), so 5 rooms starting a round in the same second are
   about 250 deliveries. With the Pro default of 500 connections the site holds about 9 full rooms next to its
   other visitors.
2. `go v12-g4-live.sql` (and `go v12-g4-party-rls.sql`, optional: it does nothing in production today).
3. Tracking counts one run per phone, so a 50 player room adds 50 runs and each song 50 plays. If rooms should
   count once instead, say so: it is one function in `use-player.ts`.
4. "Share results" on the podium is not built (no results page exists). Wanted?
5. The host needs two players to start (the prototype's rule); the server accepts one.
6. A removed player can join again under another name (no account, nothing to ban); the host removes again.
7. Closed real rooms keep one row (code, playlist, rounds played, peak players, no personal data) for the
   weekly counts; no purge is scheduled. Test rooms are deleted.
