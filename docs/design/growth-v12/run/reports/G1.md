Tracking (its own switch, `NEXT_PUBLIC_BT_TRACKING`, default off):
- `lib/tracking/bt-shared.ts` (vocabulary and pure helpers, no import), `lib/tracking/bt.ts` (browser:
  `trackBtRun`, `newBtRunId`, `btSourceHere`, `btLocale`, `btChallengeCodeHere`), `lib/tracking/bt-server.ts`
  (validation, clamps, user agent class, `is_test`, rate limiter, "not live" detection).
- `app/api/track/bt-run/route.ts`: `start` and `finish`. Off: 404 for every method. On: reads the body as text
  (a beacon is `text/plain`), drops bots on the user agent, validates and clamps, rate limits per anon id
  (60 events / 10 min) and per IP hash (300 / 10 min, `sha256(ip + day)` kept in memory only), writes with the
  service role. `start` = insert, a repeat keeps the first row. `finish` = update of the open row
  (`finished_at IS NULL`, same anon id), else insert of the whole run when the start was lost. A second finish
  writes nothing. `bt_bump_song_plays` is called once per written finish and never when `is_test`. The player
  never gets an error: table missing = `200 {ok:false, reason:'not_live'}`, anything else = `200 {ok:false}`
  (429 only for the rate limit). The anon id is mirrored in the httpOnly `nq_anon` cookie after a written row,
  which is what the claim trusts.
- `is_test` = `process.env.VERCEL_ENV !== 'production'`. Nothing in the route or the rules reads the Host
  header or the request URL (a unit test scans for it).
- `components/blindtest/ux-v1/use-run.ts`: start when the first clip really plays (`playing` event), finish on the
  results (completed) or on quit, a new start, unmount, `pagehide` (completed = false, `sendBeacon`). Covers
  playlists, groups, theme pages, daily, challenge. `startChallenge` takes an optional third argument (the code).
- `components/blind-test/use-bt-tracking.ts` (new, shared by the two legacy games), wired in
  `blindtest-game.tsx` (hub, daily, quit button) and `blind-test-player.tsx` (playlist pages).
- `app/api/claim-runs/route.ts`: also attaches unowned `bt_runs` of the cookie-proven anon id (same contract,
  behind the switch, soft: a missing table or a failure of this one update leaves the existing claim intact).
- `app/(site)/admin/blind-tests/runs/page.tsx`: 404 when the switch is off, admin gate like the other admin
  pages, one RPC (`bt_runs_admin_stats`), windows of 7, 30, 90 days: runs today, runs, completion rate,
  players, completed, abandoned, signed-in and guest runs; runs per day, per source, per playlist, per mode;
  runs per player (1, 2 to 4, 5 to 9, 10 or more); top songs and hardest songs. Test runs and bots excluded,
  counts only. Before the SQL file is applied it says so instead of showing zeros.
- `docs/pending-migrations/v12-g1-bt-runs.sql`: `bt_runs` (RLS on, no policy, grants revoked from anon and
  authenticated), four indexes, `bt_song_stats` (`security_invoker`), `bt_bump_song_plays(uuid[])` and
  `bt_runs_admin_stats(integer)` (execute for `service_role` only). Header: what, why, rows, unlocks, safety,
  order, verify, undo.

Vocabulary recorded: `playlist` = `all`, `group:<slug>` (several groups: `group:a+b`), `theme:<generate id>`
(`theme:gg`, `theme:3rd-gen`, `theme:hits`), `daily:<utc date>`, `challenge:<code>`. `mode` = `classic` for every
flow of today (generate has no clip length, so the "speed" and "intro" pages really play 10 second clips).
`score` = the v11 points on the v11 game, the right-answer count on the legacy games.

## 5. What went wrong once

On the first run of the spec two tracking beacons left the browser while Playwright was tearing a page down
(a run still open when the test ended, and a real navigation in the pagehide test), so they were not caught by
the stubs and reached the dev server's real route with valid payloads. Nothing was written: `bt_runs` does not
exist (checked right after: `to_regclass('public.bt_runs')` is null, `songs.play_count` still 0 everywhere).
The spec now closes every run before a page goes away, dispatches `pagehide` instead of navigating, and adds a
context-level stub for the endpoint. The three later runs were checked against the server log (section 3).
The same trap waits for any other spec that plays a blindtest with the switch on once the table exists
(request R5).
