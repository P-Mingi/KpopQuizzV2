## 2. Technical SEO (codebase)

The technical foundation in the repo is strong. Most of the prior indexation
brief (`kpopquiz_seo_indexation_fix.md`) was actually implemented in A1-A4. The
items below are what remains.

### 2.1 P1: robots.txt blocks pages that also carry noindex

`src/app/robots.ts` disallows `/login`, `/onboarding`, `/settings`, `/admin`,
`/auth/`, `/api/`. Live `robots.txt` confirms this is what is served.

But these routes now also set `robots: { index: false }` via their layouts
(`login/layout.tsx`, `onboarding/layout.tsx`, `settings/layout.tsx`,
`admin/layout.tsx`). That is the conflict the prior brief warned about: if a URL
is disallowed in robots.txt, Googlebot cannot fetch it, so it never sees the
noindex tag, and a URL that picked up links can stay stuck in the index with a
"Indexed, though blocked by robots.txt" status.

Fix in `src/app/robots.ts`: remove `/login`, `/onboarding`, `/settings` from
`disallow`. Keep `/api/` and `/auth/` blocked (those are not meant to render
indexable HTML and have no noindex). For `/admin`, either keep the robots block
or rely on its noindex, but not relevant for indexation either way. Net new
disallow list:

```
disallow: ['/api/', '/auth/']
```

Rely on the per-route `noindex` meta for `/login`, `/onboarding`, `/settings`,
`/admin`, `/search`, `/profile`, `/banned`. They already have it.

### 2.2 OK: sitemap is well built

`src/app/sitemap.ts` is solid: it caps result counts, wraps DB queries in
try/catch so a DB blip returns static pages instead of a 500, skips `-quiz` hubs
with zero quizzes (avoids soft-404 thin pages), and only lists `-trivia` URLs for
groups with enough unique facts to render. Quiz URLs use `/q/{slug}`, which
matches the real route. No action required.

One forward-looking note: quiz cap is 10000 and a single sitemap maxes at 50000
URLs. Fine today. When quizzes approach that, split into a sitemap index.

### 2.3 OK: metadata, canonicals, JSON-LD

Per-page unique titles, descriptions, and self-referencing canonicals are
present in the repo: `q/[slug]/page.tsx` (Quiz schema + canonical `/q/{slug}`),
`[slug]/group-quiz-page.tsx` (CollectionPage + ItemList, canonical
`/{slug}-quiz`), the home page (WebSite schema with SearchAction), and the
category pages. `noindex` is correctly applied to non-content routes and to thin
profile pages (`u/[username]` when `total_quizzes_created < 3`). This is good
work. It only needs to ship (Section 0).

### 2.4 P2: redirect hops in navigation

`next.config.ts` 308-redirects `/ranks` and `/hall-of-fame` to `/leaderboard`.
The live nav still links to `/ranks` and `/hall-of-fame` (old build). In the
redesign, point nav and footer links directly at `/leaderboard` so users and
bots skip the redirect. Verify the nav component after deploy and update any
remaining `/ranks` or `/hall-of-fame` hrefs.

### 2.5 OK: redirects for legacy URLs

`next.config.ts` permanently redirects `/group/:slug` to `/:slug-quiz` and the
old `how-well-do-you-know-{group}` URLs to the same hubs. This resolves the "3
redirecting group pages" item from the prior brief. Good.

## 3. Rendering and performance

### 3.1 P2: ISR is configured but dormant

`q/[slug]/page.tsx`, `[slug]/page.tsx`, and the home page all set
`export const revalidate = 3600`, but the in-code comments are honest about the
catch: the shared `<TopNav>` calls `auth.getUser()` (reads cookies), so every
route opts into dynamic SSR and the ISR window never activates. The SEO content
is still server-rendered (good), but there is no static/CDN cache, so TTFB is
higher and origin load scales with traffic.

Opportunity (not urgent): make the top nav cookie-free for the public shell
(render a neutral nav server-side, hydrate the signed-in state client-side), or
move the auth read into a leaf component wrapped so the page can be static. Then
the existing `revalidate` windows start working and public pages get CDN-cached
HTML. This helps Core Web Vitals (TTFB/LCP) and crawl efficiency.

After production deploys `main`, re-run the prior brief's verification:

```
curl -s https://kpopquiz.org/q/<slug> | grep -i "quiz-review\|application/ld+json\|rel=\"canonical\""
```

All three must appear. (Today they do not, because the build is old.)

## 6. Keyword and brand strategy (the "io" question)

You observed that the site gets impressions for `kpopquiz.io`, `kpop quiz io`,
`kpopquiz io`, etc, but not for plain "kpop quiz" / "kpopquiz" / "kpopquizzes".
Here is what is happening and what to do.

### 6.1 Why "io" queries show but core terms do not

- `kpopquiz.io` is a different, live competitor (an emoji song-guessing game). It
  ranks number 1 for its own brand. When people search the `.io` brand, Google
  also surfaces `kpopquiz.org` as a close alternative, so you collect impressions
  on those navigational queries. There is also a `kpopquiz.com`. Three different
  sites share the "kpopquiz" name, which dilutes the brand entity.
- The generic head term "kpop quiz" is owned by very high-authority incumbents.
  A live SERP check for "kpop quiz" returns Quotev, BuzzFeed, Sporcle, JetPunk,
  KProfiles, Soompi, and the V&A. `kpopquiz.org` is not on page one. With the old
  thin build (Section 0) and a young domain, you simply do not have the authority
  or the indexed, unique pages to rank for that head term yet.

So the "io" impressions are a brand-collision artifact, and the missing core-term
impressions are an authority + indexation problem, not a tracking bug.

### 6.2 Strategy: win the winnable terms first

Do not fight "kpop quiz" head-on yet. Target group + intent long-tail, which is
exactly what the `/{group}-quiz` and `/{group}-trivia` hubs are built for:

- "bts quiz", "blackpink quiz", "stray kids quiz", "seventeen quiz", "twice quiz",
  "ateez quiz", "txt quiz", etc.
- "how well do you know {group}" (you already redirect the legacy URLs here).
- "{group} trivia", "{member} quiz", "guess the kpop idol", "kpop true or false"
  (you already have dedicated pages: `/guess-the-kpop-idol`, `/kpop-true-or-false`,
  `/kpop-quiz-2026`, `/easy-kpop-quizzes`, `/hard-kpop-quizzes`).

These have real, satisfiable intent and far less authority gatekeeping. Each hub
already has unique content and internal links. The job is: deploy them, get them
indexed, then expand coverage (more groups, more member-level pages) and keep
them fresh around comebacks.

### 6.3 Strengthen the brand entity

To stop losing ground to `.io` and `.com` on brand searches:
- Add Organization JSON-LD in `src/app/layout.tsx` with `name`, `url`, `logo`, and
  `sameAs` pointing to your real social profiles and Reddit. This helps Google
  treat `kpopquiz.org` as a distinct entity.
- Make the footer socials real links (Section 7.2), and keep handles consistent
  across profiles so the brand signal is coherent.
- Consider a short, keyword-aware brand line in `<title>`/H2 ("KpopQuiz, free
  K-pop quizzes") so brand and category co-occur.

### 6.4 Data to pull from GSC to confirm (Section 8)

Once the GSC export is readable: sort queries by impressions, split into
"io/brand-collision", "our brand", and "generic/long-tail". Expect most current
impressions to be brand-collision and group long-tail. Track group long-tail
clicks as the deploy lands and pages index.

The group hubs expose a `noscript` list of every quiz, related-quizzes blocks
link with real `<a href>`, and legacy URLs 308 to canonical hubs. Internal
linking for crawl is in good shape once deployed. No broken internal targets were
found in the repo beyond `/contact` and the stale `/cards` to confirm (5.2).

stale, so crawling it now audits the wrong pages).

```tsx
        'https://reddit.com/r/Kpop_Verse',
```

Only include `sameAs` URLs that are real and live. This helps Google separate
`kpopquiz.org` from `kpopquiz.io` and `kpopquiz.com`.

### Step 9 (P2, larger task): make the nav cookie-free so ISR activates

Today `<TopNav>` calls `auth.getUser()` (reads cookies), forcing every public
route to render dynamically, so the `export const revalidate = 3600` windows on
the home, `q/[slug]`, and `[slug]` pages never cache.

Goal: render a neutral nav shell server-side (no cookie read) and hydrate the
signed-in state client-side (client component that fetches the session after
mount). Once the public render path no longer reads cookies, the existing
`revalidate` windows produce CDN-cached HTML.

Steps:
1. Split `top-nav.tsx` into a server shell (logo, primary links, no auth) and a
   small client `AuthMenu` that loads the user client-side.
2. Remove the server-side `auth.getUser()` from the shared layout/nav path on
   public routes.
3. Verify a public route is now static/ISR: `curl -sI https://kpopquiz.org/` and
   look for a cache hit header (for example `x-vercel-cache: HIT` on a second
   request), and confirm signed-in UI still hydrates.

This is performance and crawl-efficiency, not correctness. Schedule after the P0
and P1 items.
